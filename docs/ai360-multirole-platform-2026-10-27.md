# РЕСАНТА AI 360° — единый мультиролевой голосовой помощник (архитектурный контракт)

Дата: 27.10.2026. Статус: **подготовка платформы, не выпуск сотрудникам**.

## Цель
Одно ядро понимания естественной речи для ДФС, ДФ и МПП. Не писать регулярные выражения под каждую фразу.
Голос, текстовый чат и в будущем AI-очки — разные адаптеры одного проверяемого server conversation gateway.

## Проверенный аудит существующей CRM
- `users` содержит `id,role,region,access_scope`: `boss`, `manager`, `office_manager` и другие. **Различие ДФС/ДФ не выражено только полем role**; сеть нельзя открывать всем `boss`.
- `clients`, `purchase_history`, `visits`, `route_plans`, `client_debt`, `promotions`, `payment_registry` существуют в Supabase. Источники VIP и Триовиста доступны через отдельные таблицы/RPC.
- Текущие `crm-voice-transcribe-v1`, `crm-voice-yandex-tts-v1` и `crm-ai360-director-v1` допускают только одного директора. Для ДФ и МПП требуется новый серверный вход и авторизация до любых чтений.
- У будущего Гомеля пока нет явной проверенной сетевой membership-конфигурации в существующей голосовой платформе.

## Техническая архитектура
1. **Адаптеры**. Браузер Mac/Windows, позже Android после регрессии, и очки с поддерживаемым каналом аудио. Никакой адаптер не получает service-role ключи, право читать базу целиком или обходить шлюз.
2. **Conversation gateway**. JWT через `auth.getUser`; серверно получает профиль и доверенную принадлежность к филиалу/менеджеру. Сессия не зависит от распознанных имён, названий филиалов и слов «я директор».
3. **Память диалога**. Серверное состояние (actor, scope, focus_manager/client, selected_period, last_domain, pending_action), ключ по пользователю+случайной сессии, TTL. Смена филиала/аккаунта никогда не наследует старую память. История — только контекст, не доказательство цифр.
4. **Планировщик намерений**. LLM разбирает свободный вопрос на домены и конкретные *разрешённые* операции. Набор доменов расширяется регистрацией tools, без хардкода клиентских фраз. Выход модели недоверенный: сервер валидирует схемы, права и ограничения ресурсов.
5. **Реестр проверенных инструментов CRM**. sales/kpi, clients/visits/routes, debt, promotions+ROI, payment_registry, VIP DFS/DF/MPP, Triovist/21vek, tasks. Каждый инструмент выдаёт источник, дату обновления, валюту/НДС, scope, warnings и ограниченный набор записей.
6. **Аналитика**. Модель строит выводы только из разрешённого evidence. План≠факт; просрочка≠доказанное невыполнение; маршрут≠посещение; падение закупок≠заказ; действие≠выполненный платёж.
7. **Actions gateway, отдельный от чтения**. Сначала проект действия → точное разрешение записи и повторы/изменения проверяются сервером → подтверждение *конкретного объекта* → повторная проверка статуса → запись только через действующую защищённую RPC → аудит. Никакого реального действия из общего «согласовано».
8. **Наблюдаемость**. Временные метки, request_id, selected_tool, source_freshness, duration, отказ доступа, результат. Не писать секреты, полный звук и коммерческие документы в обычные логи.

## Матрица данных
- **ДФС** — вся согласованная белорусская сеть, VIP и Триовист, аналитика планов, расходов, ПДЗ, акций, платежи с самостоятельной проверкой права на согласование.
- **ДФ филиала** — только подтверждённая территория его филиала, сотрудники, планы, клиенты, маршруты, акции, ПДЗ; платежи только если существующая роль/RPC прямо допускает чтение. Никакого доступа к чужому филиалу по просьбе в голосе.
- **МПП** — только назначенные ему клиенты, посещения, маршруты, задачи и условия, доступные его CRM-роли; возражения и подготовка к встрече разрешены, но не гарантируют заказ.
- **Менеджер Триовиста** — отдельный явно делегированный scope, не равный полному сетевому доступу.
- **Гомель** — отдельный `branch_id` и контролируемые назначения, до появления назначений доступ не включается.

## Важные границы по согласованию оплат
«Лера, согласуй оплату» не должно менять `payment_registry` без указания ровно одной заявки. Система озвучивает сумму, валюту, получателя/описание и ID/номер записи, спрашивает отдельное подтверждение, проверяет права текущего пользователя и актуальный статус, журналирует решение. **Согласование заявки в CRM — не отправка денег в банк.** Возможность реального голосового решения не включается пока нет полного теста и отдельного action gateway.

## Приёмочные сценарии
- «Привет, Ресанта. Что важного?» → аналитика своего scope.
- «Как выполняет план Шкуран?» → verified plan/fact с НДС и датой обновления.
- «Кого давно не посещал?» → только закреплённые клиенты, дата, маршрут, отсутствие дублей.
- «А что с задолженностью? А теперь с акциями? Какие эффективны?» → связная смена домена, верное evidence.
- «Что с VIP ДФС? А с VIP ДФ?» → реальные различия на разрешённых срезах.
- «Триовист по категориям за квартал» → только проверенные источники.
- «Какие оплаты ждут меня? Согласовано» → сначала конкретный черновик подтверждения, без CRM-записи на этапе MVP.
- МПП «Куда заехать сегодня? Что ответить клиенту, который считает цену высокой?» → существующий маршрут + клиентские факты + помощь с возражением.
- ДФ Гомеля пытается получить данные Витебска или платежи ДФС → отказ на сервере.
- Старый ответ/имя в истории, промпт-инъекция в комментарии клиента, подменённый `focusManager` → не расширяют права.
- Повторные голосовые команды, скрытая вкладка, выход/смена учётной записи → микрофон и память не смешиваются.

## Реализация и порядок включения
1. Pure role/scope kernel + unit tests (эта ветка). `trustedBranchId`/manager membership допустимо передавать только из серверных связей, не из браузера.
2. Создать реестр инструментов и изолированный conversation gateway, подключить read-only домены с доказательными snapshot.
3. Безопасное серверное состояние и end-to-end тесты на диалогах с переходами разделов.
4. Пилот ДФС, затем явно назначенный ДФ Витебска, потом МПП, Гомель после создания филиала и назначения прав.
5. Отдельно action gateway платежей и поручений с audit trail, после безопасной read-only стабилизации.
6. Очки подключать к тому же backend только после проверки конкретной модели и её возможностей (микрофон, API, экран/звук, безопасность). Не строить бизнес-логику внутри прошивки очков.

**Запрет до полного ролевого аудита:** НЕ заменять старый защищённый director-only endpoint на `role === boss`; НЕ открывать service role клиенту; НЕ объединять директорские и МПП данные в общий LLM evidence; НЕ включать реальные действия из свободной речи.

# ИИ-аудит месячных маршрутов — первый этап (21.10.2026)

## Как работает
- Только директор (роль `boss`), только после открытия раздела «Маршруты», только по кнопке «ИИ-анализ маршрута».
- Месяц берётся из селектора `#rb-coverage-month`; фильтр менеджера — из существующего фильтра.
- Плановые точки читаются из `route_plans`; фактические визиты — из `visits`; месячные прозвоны — из `tasks`. Ничего в этих таблицах не изменяется.
- Продажи суммируются в RPC `crm_route_audit_sales_v1` по **3 завершённым месяцам** до начала выбранного месяца (не позже последнего завершённого месяца относительно текущей даты), против аналогичных трёх месяцев прошлого года.
- Для сопоставления используется точный `client_id`, не имя клиента: это исключает ошибочные финансовые рекомендации для клиентов с похожими названиями.
- Условия сигнала о падении: предыдущий период ≥500 BYN, снижение ≥20%, разница ≥500 BYN, физического визита нет. Разница называется **историческим разрывом продаж**, не прогнозом.
- Давность визита ≥45 дней; потенциальный клиент в том же городе, что запланированный визит менеджера; повторные визиты с промежутком ≤3 дней.
- «Лишние переезды» — только при явной последовательности ≥4 геоточeк и превышении ≥25 км и ≥35% **геометрического расстояния**. Это не дорожный километраж.
- Сигналы не означают виновность сотрудника: решение только ДФ, без автоматического исправления плана.
- Решения ДФ (согласовано/отклонено/обсудить) записываются отдельно в `route_month_ai_reviews`; RLS разрешает их только руководителям через `crm_is_boss()`. Планы и задачи не меняются.

## Производительность и безопасность
- Скрипт загружается лениво только на странице маршрутов; запросы запускаются **только нажатием**.
- Суммирование продаж выполняется в БД; не скачивается полный массив строк истории продаж.
- Все показываемые текстовые поля экранируются.
- SQL-функция работает как `SECURITY INVOKER`, возвращает пустой набор не-руководителям.
- Новая таблица закрыта для `anon`; прямой доступ к решениям контролируется RLS.

## Ограничения первого этапа
- Не используется LLM; первый этап — проверяемые детерминированные аналитические правила. Формулировка «ИИ» обозначает помощника по анализу, не выдуманные предсказания.
- Коммерческие рекомендации возможны только для клиентов с продажами, привязанными к `client_id`. Интерфейс раскрывает число клиентов без такой истории.
- Отсутствие фактического визита в базе не приравнивается к отсутствию встречи в действительности.
- GPS-разбор прошедшего дня, классификация остановок и будущая генерация черновиков маршрутов не входят в первый этап.

## Проверка
1. Авторизоваться директором, открыть «Маршруты», выбрать месяц, нажать анализ.
2. Сверить выбор периода и несколько примеров падения с историей `purchase_history`.
3. Принять / отклонить / обсудить сигнал; повторить анализ — решение сохраняется.
4. Войти менеджером: кнопка и решения недоступны.
5. Убедиться, что `route_plans`, `visits`, `tasks` не изменились после анализа/решения.

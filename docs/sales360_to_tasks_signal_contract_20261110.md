# Продажи 360° → Задачи · договорённость по интеграции (10.11.2026)

## Цель
Связать обнаруженные на подтверждённых данных 1С падения продаж и коммерческие возможности из «Продажи 360°» с модулем «Задачи ИИ», **при его следующей доработке**. Текущее внедрение не создаёт задач и не меняет действующий модуль.

## Текущее API сигналов
На клиенте Sales 360 есть чистый детерминированный метод `window.RESANTA_SALES360_V1.directorSignals(annualData)`, где `annualData` — защищённый результат `crm_sales360_annual_v2`. В будущей интеграции источником должен быть **новый защищённый серверный RPC**, повторяющий правила, а не доверие к переданному браузером JSON.

Каждый кандидат для будущей задачи:
- `signal_key`: `sales360:decline:<год>:<категория>` или `sales360:opportunity:<год>:<менеджер>:<категория>`.
- `kind`: `decline` / `opportunity`.
- `year`, `manager`, `category`, `source_period`, `source_import_timestamp`.
- `revenue_current`, `revenue_previous`, `loss_byn`, `loss_pct` — только подтверждённые, одинаковые **закрытые месяцы** двух лет.
- `priority`, `evidence`, `hypothesis` (прямо помечать как гипотезу), `suggested_action`, `proposed_owner`.
- `status`: новый → на проверку → согласован руководителем → в работе → выполнен / отклонён.
- `source_version`, `last_checked_at`, `accepted_at`, `decided_by`.

## Правила детектирования v1
- Снижение группы: прошлогодняя база ≥10 000 BYN, спад ≥5 000 BYN **и** ≥10%; высокий при ≥20 000 BYN и ≥15%.
- Учитывать только сопоставимые завершённые месяцы, не сравнивать неполный ноябрь с полным ноябрём прошлого года.
- Отсутствие продаж у менеджера при продажах коллег — **повод проверить**, не диагноз «не знает продукт».
- Обязательно проверять возвраты, изменение клиентской базы, ассортимент, остатки, сезонность, отменённые заказы и переводы клиентов.
- Исключить повторение `signal_key` при каждом обновлении импорта. Обновлять суммы в существующей записи и хранить историю.
- Суммы из «Триовист 360°» отдельно не добавлять в выручку филиала.

## Декомпозиция группа → подгруппа → SKU при создании задачи
Главный сигнал должен группировать проблему по менеджеру + товарной группе + сопоставимому периоду; внутри задачи показывать **вклад подгрупп** и затем **конкретные SKU**, а не создавать по одному поручению на каждый артикул. При проверке конкретного клиента — указывать его подтверждённый CRM client_key.

В будущем по нажатию на сигнал Tasks читает те же подтверждённые агрегаты, что и `crm_sales360_product_drill_v3`, но через серверное проверенное чтение с отдельным аудитом. Руководитель видит: группа упала на X BYN, из них подгруппа A — на Y, подгруппа B — на Z, ключевые SKU — с фактами двух лет. Это *объяснение состава снижения*, а не доказательство причины.

Поручение имеет измеримый итог: кто проверяет, кого из клиентов нужно посетить, что в наличии, какие коммерческие предложения согласовать, срок, проверка исполнения через фактическую выручку 1С. При повторном импорте обновлять сигнал и связанные факты, но не создавать дубль.

## Безопасность и ответственность
Только менеджер видит свой срез, директор — весь филиал. Создание **реального поручения** возможно после утверждения директором или после отдельного согласования автоматического правила назначения, ролей, дедупликации и журнала аудита. Не создавать экзамены автоматически. Нельзя писать в таблицы задач при простом открытии «Продажи».

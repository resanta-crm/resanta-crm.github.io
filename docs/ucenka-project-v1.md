# Resanta CRM — проект «Уценка» v1

## Рабочий промт для ChatGPT

Ты отвечаешь за модуль «Уценка» в Resanta CRM. Реализуй его как отдельный быстрый page-scoped продукт внутри существующей CRM и никогда не ухудшай скорость других разделов.

### Бизнес-смысл
Уценка — товар, возвращённый клиентом или сервисом, который нужно продать повторно. Уценённый товар сохраняет гарантию. Без явных задач менеджеры не должны считаться ответственными за реализацию.

### Источник данных
1С присылает полный реестр уценки на почту. Тема письма содержит «Уценка» и «CRM». Вложение XLSX.
CRM импортирует реестр автоматически, не загружая эти данные при старте приложения.

### Карточка уценки
Каждый возврат/партия — отдельная карточка, даже если артикул совпадает, потому что состояние, фото и скидка могут отличаться.
Карточка содержит:
- уникальный ID/Ключ 1С;
- артикул;
- номенклатуру;
- количество;
- базовую цену;
- источник/причину возврата;
- документ и дату;
- серийный номер при наличии;
- комментарий 1С;
- фактическое описание состояния;
- гарантию;
- фотографии;
- скидку и финальную цену;
- назначения менеджерам;
- факт реализации.

### Права
- Видят раздел: все зарегистрированные пользователи CRM.
- Фото и фактическое описание состояния: все зарегистрированные пользователи.
- Утверждать скидку/финальную цену: только Александр Паюшин (payushin_ar@resanta.ru).
- Ставить план менеджеру и мотивацию/демотивацию: только Александр Паюшин.
- Менеджер может фиксировать продажу только по своей назначенной задаче.
- История изменения цены обязательна.

### Фото
- Мобильная камера и галерея прямо из карточки.
- Приватный bucket markdown-photos.
- Общий вид, дефект, шильдик/артикул, упаковка, другое.
- Изображения по возможности сжимаются на устройстве перед загрузкой.
- Фотографии не должны загружаться глобально при старте CRM.

### Продажа и задачи
После назначения менеджера CRM создаёт обычную задачу source=markdown_sale.
Задача содержит:
- товар и артикул;
- финальную цену;
- план в штуках;
- срок;
- гарантию;
- ожидаемый результат и критерий факта продажи.
Мотивация и демотивация хранятся в назначении и должны быть видны Александру Паюшину и назначенному менеджеру.

### Производительность — обязательный инвариант
- Модуль загружается только при открытии страницы markdown.
- Никаких MutationObserver по всей CRM.
- Никаких глобальных setInterval.
- Никакого добавления данных уценки в основной bootstrap/loadData.
- Повторный вход показывает уже готовый DOM немедленно; тихое обновление — только если кэш старше 60 секунд.
- Изображения получают signed URL только для отображаемых карточек.
- Почтовый импорт работает отдельно через GitHub Actions и не блокирует браузер.

### Безопасность
- Бизнес-таблицы закрыты RLS и не доступны напрямую authenticated/anon.
- Все операции идут через узкие security-definer RPC с проверкой email/пользователя.
- Storage bucket приватный.
- Никаких ключей/паролей/секретов в GitHub-коде.

### Этапы
1. Реестр + поиск + фото + состояние + гарантия.
2. Цена/скидка Паюшина + аудит.
3. План менеджеру + задача + мотивация/демотивация.
4. Факт продажи + KPI/просрочка.
5. Умная рекомендация клиентов и AI-помощник продажи.
6. Аналитика: остаток уценки, срок лежания, конверсия, потери/возврат стоимости, рейтинг менеджеров.


## Контроль продаж по 1С · v23.6.91

Продажа уценки не считается окончательной по нажатию менеджера.

Цепочка:
1. Менеджер с назначенной задачей нажимает «Заявить продажу».
2. Количество указывается менеджером, но цена берётся только из утверждённой Александром Паюшиным финальной цены.
3. Для продажи обязателен клиент:
   - клиент CRM выбирается через отдельный серверный поиск;
   - либо «Розница / другой клиент» с обязательным комментарием.
4. Создаётся неизменяемая заявка со статусом «Ждёт 1С».
5. Следующий полный отчёт «Уценка для СРМ» сравнивает старый и новый остаток:
   - уменьшение на заявленное количество → продажа подтверждена 1С;
   - остаток не уменьшился / уменьшился не на заявленное количество → расхождение;
   - уменьшение остатка без заявки → системный сигнал;
   - исчезновение SKU без заявки → системный сигнал;
   - повторное появление ранее отсутствовавшего SKU → системный сигнал.
6. Обычная задача менеджера закрывается только после подтверждения продажи 1С либо после ручного решения Александра Паюшина.
7. Все ручные решения Александра Паюшина записываются в отдельный аудит.
8. Контроль продаж и денежные детали доступны Александру Паюшину в отдельном блоке «Контроль продаж».

Производительность:
- контроль не входит в глобальный bootstrap;
- список контроля загружается только по нажатию;
- основной модуль остаётся без глобальных setInterval и MutationObserver.
